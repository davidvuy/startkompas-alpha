# Four-week improvement roadmap

This is a proposed sequence of work, not a delivery guarantee or a claim that user validation has happened. Each week should produce a usable increment. Fix critical defects before expanding scope. The original version-1.0 acceptance requirements remain separate.

## Week 1 — Make the first experience dependable

- Publish clear question, bug, feature and private-security reporting routes.
- Run redacted secret scanning on public pushes and pull requests.
- Provide a reproducible fictional demo and guided setup instructions.
- Observe willing users installing and resuming; record friction without collecting private dossiers.

Exit evidence: passing public CI, a verified walkthrough and documented first-use findings when participants are available. Missing participants remain an explicit evidence gap.

## Week 2 — Complete one useful founder workflow

- Prioritize the most common observed blocker.
- Improve the idea-to-first-offer route, keeping sources and uncertainty visible.
- Make the next action and resume experience understandable.
- Add regression coverage for reproduced failures.

Exit evidence: a complete fictional reference workflow and, where available, voluntary user feedback about usefulness. No invented time-saving claims.

## Week 3 — Make changes and recovery trustworthy

- Improve change impact explanations and readable exports where feedback supports them.
- Exercise backup/restore and malicious imported-content boundaries.
- Review dependency updates, privacy documentation and remaining security limitations.
- Seek independent review when a suitable reviewer is available; do not label an internal check independent.

Exit evidence: reproducible recovery checks, targeted regression results and an explicit list of unresolved risks.

## Week 4 — Make contribution and reuse easier

- Refine tutorials, public contribution guidance and small contribution tasks.
- Publish a changelog and supported-environment table based on actual tests.
- Incorporate consenting users' experiences; measure voluntary return rather than stars alone.
- Choose the next milestone from evidence, including simplifying features that do not help.

Exit evidence: a reviewed release candidate, maintained documentation and an evidence-based next backlog.

## Why contribute or fork?

A public repository can be copied. Our goal is to make the maintained project valuable through tested workflows, understandable decisions, dependable updates and useful documentation, rather than artificial complexity. A fork retains a connection to upstream history and makes it easier to propose changes back.

Before a large change, open an issue describing the user problem and a fictional example. Keep changes focused, run the tests and never commit private data. Follow LICENSE and LICENSING.md; permission to use code does not automatically grant rights to branding or imported material. There is no automatic acceptance or support promise for forks.
