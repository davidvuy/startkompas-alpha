# Possible research conflicts

Flag two distinct saved research fragments as a possible conflict in audience, amount, capacity or conditions. State their shared situation and the suspected difference explicitly. The candidate preserves the two finding fingerprints and assumption snapshots. Reusing the same fragment through two links is rejected, and reversing the same pair does not create another candidate for the same category/context.

Candidates are entered by the user. There is no automatic language/number extraction or AI call. Different amounts, currencies, periods, wording or experiences are not automatically contradictions. A separate user review can confirm, dismiss or request more information, with a reason and contributor alias. These are user judgments, not externally verified evidence or automatic changes to assumptions, tasks or business decisions.

Review versions retain prior decisions and the exact then-current assumptions. Changed context or unavailable/changed sources flag the current judgment as needing review. New reviews require readable unchanged sources; historical candidate and review context remains available. Source deletion removes the entire linked candidate and its review versions, including both assumption snapshots, while leaving the other original source intact. The removal preview discloses these whole-record removals and the existing external-copy limits.

Bounds: 300 candidates, 1000 reviews, 8000 UTF-8 bytes per context/reason field, 800 per contributor alias and 128 KiB per saved record. Strict shape, ancestry, fingerprint, archive and current-state checks apply. Tests are synthetic. The authenticated local API exposes list, candidate preview, separate review preview and explicit save with project/origin/kind/confirmation/current-state/retry guards. Browser controls provide a candidate list, explicit two-fragment/category/context selection, side-by-side original content, separate review decision/reason, immutable history and preview/confirmation with dirty navigation guards. The original unsaved-offer concurrency controls remain separate. Edge verification covers distinct-fragment candidate creation, an explicitly separate dismissal, saved review history, edit-triggered preview/confirmation reset, dirty project-switch refusal and inert source text. Responsive layouts and browser review after source/context changes remain pending; helper/API tests cover state guards.
