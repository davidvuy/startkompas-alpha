# Source retention and known copies

Per-source retention records store optional review and retention-until dates, a reason and a contributor alias. Dates due today or earlier are flagged for attention. They do not trigger automatic deletion, imply legal compliance or establish permission to retain personal information. Later records supersede earlier reminders while preserving their history.

The source management inventory identifies the selected inbox item, explicitly linked conversation notes, source summaries and research findings targeting that source or those conversations, plus their classification records and whole linked conflict candidates/reviews. Summaries retain full source snapshots; findings retain excerpts/context; conversations have independently entered text that may contain additional personal data. Unlinked text copies are not detected. This is not a complete PII scanner.

The existing save route also writes retry bundles outside the project. Exports, backups, copied folders and retained browser recovery data may exist separately. The source-removal helper now removes an explicitly previewed source and its listed linked project content; see source-removal.md. Verified retry content files directly inside the project parent can be included in the exact removal preview; request/receipt metadata and unrecognized or differently located copies remain. Removal HTTP/browser controls now offer explicit whole-source/linked-copy removal and pending-operation recovery. Selective text redaction is not implemented. Browser controls support reminder preview/save, current dates, history and copy limitations; visual interaction verification remains pending. It must not be presented as completed M4-05 or data erasure.

Immutable records use the existing session/origin/current-state/archive/preview/confirmation/retry gates. Recording reminders changes no source, snapshot or external copy. Bounds: 500 reminder versions per project, strict real calendar dates and bounded readable metadata. Contributor labels are user-supplied, not authenticated identities.

## Removal implementation boundary

The generic store deliberately rejects changes to existing artifact/event records, verifies every available artifact and writes historical core snapshots. `saveGuided` also retains original content in a retry bundle outside the project. A replacement note or a hidden UI row would therefore not remove the original personal information.

The dedicated helper implements a previewed project-file privacy operation to enumerate selected original and linked snapshot files; bind the exact project revision and file hashes; preserve non-sensitive tombstones for references; handle interrupted execution and retry without resurrecting content; and report exactly which project files were removed. Verified local retry content files are now listed and removed through the same resumable transaction; excluded or differently located copies remain. Unknown/unlinked copies and prior exports remain outside any completeness claim. Do not weaken the generic append-only update route or silently erase other sources when removing one selected source. Test only disposable synthetic projects, including failure after each persistent stage, before exposing removal controls.

Filesystem operations must be sequenced explicitly. Node documents rename and unlink as separate operations, not a transaction spanning all these files; see the [official filesystem API](https://nodejs.org/api/fs.html). This informs the need for a recoverable application-level operation rather than assuming a set of file removals is atomic.
