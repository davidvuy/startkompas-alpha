# Source removal foundation

`prepareSourceRemoval` inventories one inbox source, its explicitly linked summaries and conversation notes, research findings targeting that source or those notes, its retention records and all linked finding-classification versions, and whole linked conflict candidates/reviews. Removing a conflict copy does not remove the other original source merely because it was compared. It also lists verified retry content files directly inside the project parent, plus excluded retry folders that need separate inspection. The preview lists whole records, including entire linked conversations. It binds the project revision and fingerprint. `applySourceRemoval` requires explicit confirmation and rechecks the exact scope; it never runs because a retention date is due.

The dedicated store operation removes those artifact files and retains technical tombstones (IDs, original fingerprints, generic events and missing availability). Dependencies become stale. Other source readers skip only recorded removal tombstones, so surviving sources remain usable; arbitrary missing/corrupt files still fail validation. Generic updates remain append-only and cannot undo tombstones. Replaying a previously committed attachment request does not restore its removed file.

Before deleting files, the operation writes a bounded journal by flushing a temporary file and renaming it. While that journal exists, normal core reads, writes and historical exports refuse access. Explicit resume completes the same request after interruption, including after core commit but before journal cleanup. The shared writer lock prevents concurrent writers; an actually terminated writer needs the existing owner-checked abandoned-lock recovery before resume. The journal contains IDs, retry locations and operation metadata, not raw source text. A retained historical core snapshot does not recreate deleted files.

Synthetic tests interrupt after journal creation, during deletion, before core commit and after core commit. A separate child process terminates after deleting a file and is then recovered. These are application/process-interruption checks, not proof against every hardware failure, filesystem race or power-loss ordering. Node's [filesystem documentation](https://nodejs.org/api/fs.html#fsfsyncsyncfd) explicitly notes that flush behavior depends on the operating system and device.

Recognized retry copies are verified against the committed operation hash, exact project identity, expected original artifact and current content/request fingerprints. Cleanup removes only the listed `content.json` files; request and receipt metadata remain. Directory links, uncommitted/modified requests and changed content are excluded and disclosed. Foreign-project requests are ignored. The parent scan stops with an error above 2000 entries; it is not recursive. New/changed verified copies invalidate an unused preview. The journal binds the original project parent and includes retry files so an interruption resumes the same cleanup.

This foundation does **not** remove unrecognized retry copies, copies in other locations, backups, existing exports, unlinked copies or other user-entered personal information. Historical core metadata remains. File removal is not secure disk erasure. Do not describe it as complete personal-data removal, compliance or selective redaction. No actual user data was removed during implementation.

The local API and source-management screen provide exact removal preview and explicit confirmation. The projects sidebar lists pending removals separately, including after restart, and provides bound recovery preview/confirmation. A confirmed recovery can release an owner-checked abandoned lock; a process that may still be running is never force-unlocked. Successful removal invalidates other held previews for that project. UI navigation clears removal confirmation and returning without confirmation does not delete files.

HTTP and synthetic recovery tests cover these routes. Actual browser interaction remains unverified because the browser control connection times out. M4-05 remains partial pending that verification; selective text redaction and complete personal-data discovery are not provided.

The removal target list is bounded by the dossier model's 10000-artifact limit and its journal by the 4 MiB core limit. This accommodates linked classification/conflict histories beyond the former2000-target cap; final core size validation still applies before deletion. The separate parent-directory inventory limit remains2000 entries. Maximum-size workloads are not a performance claim.
